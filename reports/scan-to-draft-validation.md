## Cold execution and correction

A second assistant received the saved skill, procedure, project path and existing CAAC executable, without the first assistant's base, answers or candidate. Its first run executed source intake, baseline check, discovery, collection, packet creation, apply and verify successfully without asking the owner to write intermediate files.

That run produced only a Buffer component draft. This exposed a real scope defect in the procedure: successful artifact generation could still narrow the user's project goal. The procedure now treats a supplied project directory as a project-level draft by default and requires explicit limits for any narrower result. The component output was retained as a failed project-scope attempt, not presented as full-project completion.

## Corrected independent project run

The cold assistant then reread the corrected procedure and generated a fresh project-level draft from both implementation files, without consulting the first draft. Eight CLI invocations, including schema, intake, baseline check, discovery, collection, packet, apply and verify, returned success. Eight entities and seven required questions survived publication. No target project code ran.

This run proposed one M contract with two chapters and four articles, while the first proposed S with three articles. The runs had different task instructions, a changed procedure, discovery scopes and supplementary evidence. Exact prompt/model/runbook inputs were not uniformly frozen. Therefore this disagreement cannot measure identical-input variability, establish statistical sizing reliability or be attributed solely to model randomness. Size and partitioning remain LLM proposals, not deterministic or calibrated answers. Both preserved the project purpose and full-width requirements in prose, with missing behavioral evidence and human approval open. Human review must choose the appropriate structure; artifact verification cannot settle it.

The repeated runs demonstrate that the saved skill can drive actual authoring and tool calls without owner-written intermediate inputs in this bounded environment. They do not establish success across arbitrary repositories, full legal-model coverage or semantic correctness without review.

### Failures and review-guided repair

The initial apply failed on duplicate answer IDs; the originals remain retained. The first published candidate was structurally valid but transcribed the separator alphabet in the wrong order. Because the check is substring membership rather than independent character membership, this changed the `b"zA"` and `b"Za"` boundary interpretations. Self-review and independent review found the error. A new candidate corrected the order without replacing the original.

Independent contract-first review also found unconditional clauses for steps skipped by early failure, a digest-use generalization contradicted by `none` derivation, an unspecified observed rejection exception, ambiguity between base behavior and custom overrides, and a claimed case plan that was only a coverage list. These are real authoring defects that artifact verification did not detect. Review-guided revisions add branch prerequisites, explicit base/extension scope and unresolved dependency effects, plus named concrete prose cases. Cases are not-run and unsupported runtime oracles remain questions. The repaired revisions are not new cold runs or controlled same-input repetitions.

The skill/runbook changes from these findings concern branch prerequisites, extension points, exact ordered literals and case-plan completeness. They do not introduce a semantic verifier. Those new instructions were added after this cold attempt; this run cannot demonstrate that they prevent the same mistakes in a future cold run.
