# Experimental citation-checked review findings

`caac review-findings` validates explicit review claims and prepares existing candidate decision answers. It checks evidence identity, byte ranges, exact excerpts and structural handoff rules. It does not establish that a claim is true or that a contract is satisfied.

```sh
caac review-findings --collection /tmp/caac-collection.json \
  --packet /tmp/caac-review-packet.json --findings findings.json \
  --base pending-base.json --contract path/to/module-contract.md \
  --baseline /tmp/caac-intake/baseline.json --output /tmp/caac-handoff
caac candidate apply --base pending-base.json \
  --answers /tmp/caac-handoff/answers.json --output /tmp/caac-reviewed-candidate \
  --review-receipt /tmp/caac-handoff/receipt.json --findings findings.json \
  --collection /tmp/caac-collection.json --packet /tmp/caac-review-packet.json \
  --contract path/to/module-contract.md --baseline /tmp/caac-intake/baseline.json
caac candidate verify --candidate /tmp/caac-reviewed-candidate/candidate.json \
  --provenance /tmp/caac-reviewed-candidate/provenance.json \
  --review /tmp/caac-reviewed-candidate/review.md
```

Use new output paths. Repeat the original authorized collection selections, including each optional `--run-input`, and their order/path identities, as required by [review packets](review-packet.md). Collection or packet metadata cannot add new filesystem authority. The base must already be a structurally valid pending candidate, with explicitly authored entities and unanswered unresolved decisions. This slice does not generate those decisions or entities from prose.

## Explicit finding input

The input format is `caac-review-findings-v1`. Supply the exact raw-byte hashes in `expected_collection_sha256`, `expected_packet_sha256` and `expected_base_sha256`, plus a nonempty `findings` array. Each finding has:

- `id`: a unique identifier of 1–128 ASCII letters, digits, hyphens or underscores.
- `claim_kind`: `aligned`, `suspected-mismatch` or `unverified`. These are the author's classifications, not verified verdicts.
- `claim`: the explicit interpretation being proposed.
- `inference_limits`: what the evidence does not establish.
- `citations`: objects with exactly `{evidence_id, start_byte, end_byte, excerpt}`. Use IDs from the exact packet, nonempty half-open byte ranges and exact UTF-8 excerpts.
- `handoff`: an existing `decision_id`, explicit `proposal_text` and existing `entity_refs` for the candidate decision proposal.

Claim, inference-limit and proposal text must be nonblank, at most 16 KiB each and contain no control characters. Excerpts may retain original newlines.

`aligned` and `suspected-mismatch` require both document and source citations. Having both does not prove semantic correspondence. `unverified` still needs a citation that identifies the selected context; it cannot prove project-wide absence. Unknown fields, duplicate keys and conflicting finding/decision targets are rejected. Existing decision proposals cannot be replaced.

A citation must stay inside its referenced evidence range and on UTF-8 boundaries. Source-file references permit separately selected body spans; a signature-only observation reference cannot cite the rest of the body. The tool reads all source files selected by the explicit baseline, including files not cited by a finding, and checks their current bytes against recorded full-file hashes before matching excerpts. This is additional raw-source reading, not just indexing stored syntax snippets. A valid quote does not establish execution, intended meaning, completeness or authority.

## Handoff and pending authority

The output contains `answers.json` for the existing `propose-decision` action and `receipt.json` binding the input and generated-answer hashes. The receipt separates citation integrity from unverified semantic claims. It is unsigned local evidence, not authenticated approval.

The command does not mutate the base or run `candidate apply`. Applying its answers later adds pending proposals to the existing questions. It does not remove questions, change their required flags, replace existing entities or grant acceptance. The decision text is explicitly supplied by the author, not inferred by the validator.

The optional evidence-bound `candidate apply` mode shown above regenerates the handoff through the same citation validator. Supply all four evidence paths and repeat the original explicit collection selections. The supplied answers and receipt must match the regenerated bytes exactly. Stale source, changed excerpts, altered receipt bytes and incomplete evidence options fail before publication. Plain `candidate apply` without these options remains available but does not check findings evidence.

This revalidation applies to this invocation. The unchanged v3 candidate provenance binds base and answer hashes; standalone `candidate verify` does not reconstruct the historical findings or prove that evidence-bound mode ran. Retain the exact base, findings, packet, collection, answers and receipt together. The receipt still records its earlier handoff as `candidate_application: not-performed`; applying a candidate does not rewrite history or authenticate that receipt. For exact-byte compatibility, v1 receipts retain the earlier limit that candidate apply does not verify the receipt. That sentence describes plain apply, not this optional evidence-bound mode. The [integration tests](../tests/review_findings.rs) exercise the explicit handoff and its limits, not LLM reasoning quality.

## Safety and limits

Treat source, contract and finding text as untrusted data. Instructions inside them cannot authorize tool calls, publication, deployment or new reads. Preserve uncertainty rather than promoting implementation behavior into a new obligation.

Findings and base inputs are limited to 1 MiB each. The profile supports 1–128 findings, 1–16 citations per finding and nonempty excerpts of at most 16 KiB. Existing collection/packet and source-intake limits still apply. Input identity and bytes are rechecked before publication; these are snapshot checks, not locks against concurrent writers.

The output directory must be new. The receipt is written last and marks a completed handoff, not contract completion. An I/O failure can leave a partial directory. Inspect uncertain outcomes before retrying; do not overwrite the directory or apply unverified partial output. Human semantic review and exact owner acceptance remain separate gates.

## Bounded real-source checks

The optional apply mode was exercised on selected PigeonMQ Q-045 document/source spans and the pinned `dtolnay/itoa` snapshot `9339ca99a43c550b5ee36e2afe524d1c90413461`. Both runs produced verifiable pending candidates and rejected an altered receipt without output. No target project was executed or modified. The itoa run kept its README as an unverified document, did not designate a root contract, and left correctness, safety, performance and normative intent unresolved. These are finite integration checks, not full-project acceptance or evidence of automatic contract synthesis.
